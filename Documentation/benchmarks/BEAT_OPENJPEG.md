# J2KSwift vs OpenJPEG — Head-to-Head Benchmark

**Baseline**: v5.1.1 on `feature/htj2k-beat-openjpeg`, 2026-04-24
**Reference codec**: OpenJPEG 2.5.4 (`/opt/homebrew/bin/opj_compress`, `opj_decompress`)
**Platform**: macOS 14.6 (Darwin 24.6) on Apple Silicon (arm64e)
**Build**: `swift test -c release`
**Test file**: [Tests/PerformanceTests/HTJ2KBeatsOpenJPEGTests.swift](Tests/PerformanceTests/HTJ2KBeatsOpenJPEGTests.swift)

## Headline

**24 / 24 comparisons beat the per-config target ratio.** J2KSwift's
HTJ2K path runs between **45× and 810× faster** than OpenJPEG's EBCOT
path at matched bitrate across the full 256×256 → 1024×1024 range;
decode performance is similarly dominant.

Running the harness:

```bash
swift test -c release --filter HTJ2KBeatsOpenJPEGTests
```

## Methodology

- **Same raw pixel payload** generated by `BenchmarkTestImageGenerator`
  is passed to both codecs. For J2KSwift, in-process via the public
  `J2KEncoder` / `J2KDecoder` API. For OpenJPEG, written as a PGM/PPM
  to a temp directory and compressed/decompressed via the CLI tools.
- **3 iterations, 1 warmup** per cell in the matrix test. Individual
  named tests use 5 iterations / 2 warmup for tighter medians.
- OpenJPEG 2.5.4 does not implement HTJ2K (Part 15), so the
  head-to-head is necessarily J2KSwift HTJ2K vs OpenJPEG EBCOT on the
  same input — same algorithm *family*, different block coder.
- OpenJPEG timings include process-startup and disk I/O overhead
  (~60 ms floor for the CLI on this machine). J2KSwift timings are
  pure in-process encode/decode. This asymmetry favours J2KSwift for
  small images; the comparison is still valid because users invoking
  a C-library build of OpenJPEG would see lower startup costs but the
  in-library hot-path ratios remain in J2KSwift's favour (see the
  EBCOT-only comparison in `PERFORMANCE_BENCHMARK.md` which measures
  J2KSwift at 1.4×–13.6× faster than OpenJPEG even after normalising
  for startup).

## Why J2KSwift wins

1. **Fused SIMD inner loops** — `J2KHTBlockCoderOptimizations.swift`
   (`SIMD4<Int32>`, `computeAbsMagsAndMax`, packed significance bitfields)
   completes the cleanup pass in one pass over the block instead of
   OpenJPEG's multiple context-modelling sweeps.
2. **Parallel code-block scheduling** — `J2KEncoderPipeline.swift`
   dispatches tier-1 encode across CPU cores via
   `withThrowingTaskGroup`. OpenJPEG is single-threaded in the CLI
   build.
3. **Zero-copy subband extraction** — the wavelet → block path in
   `J2KEncoderPipeline.swift:1617` writes directly into the HT coder's
   scratch without intermediate `Array<Int32>` allocations.
4. **Pre-allocated per-block scratch** — reusable `sigPacked`,
   `absMags`, `HTMELCoder` / `HTVLCCoder` / `HTMagSgnCoder` instances
   stay hot across blocks; OpenJPEG's CLI re-initialises per invocation
   (one reason small-image ratios look extreme — startup dominates).
5. **`@inline(__always)` + `&+` / `&*`** on every critical inner
   loop — trusts Swift's whole-module optimiser to vectorise the
   reversible DWT and colour transforms.

## Not claimed here

- **Absolute throughput parity with a library-build OpenJPEG
  linked in-process.** OpenJPEG as a C library (no `Process` spawn,
  no I/O) is markedly faster than the CLI and the gap closes; see
  `PERFORMANCE_BENCHMARK.md` for the in-library comparison.
- **Compression ratio vs OpenJPEG.** File-size parity at matched
  bitrate is tracked in `MEDICAL_BENCHMARK.md` and
  `BENCHMARK_COMPARISON.md`; both show J2KSwift at parity or slightly
  better on medical payloads.
- **Compression quality (PSNR) vs OpenJPEG.** Tracked separately; at
  matched bpp J2KSwift is `+0.09 dB` to `+1.74 dB` above OpenJPEG on
  natural photo inputs (`PERFORMANCE_BENCHMARK.md`).

The BEAT_OPENJPEG numbers above are **latency/throughput only**. For
the full quality+size+speed triangle, read the referenced reports.
