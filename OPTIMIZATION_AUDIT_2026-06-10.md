# J2KSwift Full-Project Optimization Audit — 2026-06-10

**Baseline:** v10.24.2 (`22100c1`) · **Method:** 8-dimension multi-agent sweep (82 agents), every finding adversarially verified against the live code AND the 13 prior lever-ceiling investigations, plus a completeness critique.
**Scope note:** codec hot-loop micro-optimizations were excluded by design (13 prior washes). Findings below are structural, allocation/copy, stale-gate, product-layer, and dead-weight items.

**Outcome:** 60 findings confirmed after adversarial verification; 13 candidate findings rejected (refuted, already implemented, or rhyming with a prior wash).


## Dimension: decoder-pipeline (7 confirmed)

> **Analyst summary:** The decoder pipeline's loop bodies are exhaustively optimized (13 confirmed lever ceilings), but the INTER-stage data plumbing has never had the same audit and carries real waste. The biggest structural item is that the lossless path abandons Int32 immediately after the iDWT: coefficients are converted to [Double] (a deferral explicitly TODO'd in code since v5.9, J2KDecoderPipeline.swift:5235-5241), then DC-unshift, multi-tile composite, and output assembly all run as separate full-image Double passes before re-quantizing to UInt16 — ~150+ MB of avoidable traffic on DX and 2x that on MG, plus a halving of peak memory if fixed. Second, a stale flag coupling at line 5145 means the default GPU iDWT (DX single-tile and MG per-tile) round-trips the intermediate LL through CPU memory on every decomposition level because the multi-level-fused branch is gated on the GPU-HT-entropy flag v10.3.0 turned off — the exact 'previously-correct routing becomes a regression' pattern v10.7 found once already. Third, the v10.4-10.8 partial/ROI product APIs parse the codestream 2-4 times per call and peekMetadata copies every tile payload it discards; compressed bytes are additionally copied 3x (tile subdata, per-block subdata, per-block [UInt8] conversion) and coefficients materialized 3x per block (C output, .map conversion, subband scatter) before the iDWT sees them. On the prompt's stub assessment: decodeQuality is no longer a stub (v10.9.0+ multi-layer packet decode shipped, routed at extractTileData line 2608); ROI Stage 3 windowed iDWT for single-tile remains the highest-value open stub since v10.24-research re-confirmed iDWT dominates single-tile DX ROI decode (the current ROI path zero-fills but still transforms the full tile); GPU truncation for partial-resolution is lower value (thumbnails are already fast and CPU-bound parse overhead — finding 3 — is the cheaper win there). Minor items not reported as findings: per-decode ProcessInfo.environment dictionary construction (J2K_PROFILE_DECODE reads), Data-subscript bit reading in packet parsing (extract stage is ~4% of wall), Data(count:) zero-fill in reconstructImage, and the DC-unshift block duplicated verbatim in four call sites (code health).

### [medium impact / large effort] Entire post-iDWT tail runs in Double for the lossless Int32 path — conversion, DC unshift, composite, and output assembly are 3-4 redundant full-image passes
**Where:** `Sources/J2KCodec/J2KDecoderPipeline.swift:4852` · **Category:** perf-hot-path

On the production lossless 5/3 path the iDWT produces flat [Int32], which is immediately converted to [Double] (line 4852-4858 vDSP_vflt32D on CPU path; line 5241 vDSPConvert.int32sToDoubles on the GPU path). Everything downstream then operates on 8-byte Doubles: colour transform (identity for the single-component medical corpus), DC level unshift via vDSP_vsaddD (full read+write pass, duplicated at lines 691-699, 1122-1135, 1259-1268, 1438-1447), multi-tile composite into full-image [[Double]] buffers (compositeTile line 1457; fullComponents alloc lines 1973-1978 / 870-875), and finally reconstructImage (line 5583) converting Double->Float->UInt16 in chunks plus a separate full byte-swap pass. For DX 6.4 MP that is a ~51 MB Double allocation plus ~150+ MB of avoidable memory traffic; for MG 16.8 MP multi-tile it is ~134 MB x2 (per-tile rgb + fullComponents) plus the passes — several ms of pure bandwidth on a decode that is now tied with Kakadu. The code itself flags this as deferred work: the comment at lines 5235-5240 ('remove or defer to final API boundary ... bigger scope tracked for a follow-up') dates from v5.9 and the follow-up never happened through v10.24. Fix: keep the reversible path in Int32 end-to-end — integer RCT (it is defined on integers), integer DC offset, fused clamp+pack to UInt16 in reconstructImage, Int32 compositeTile. Bit-exactness is preservable since all intermediate values are integers exactly representable in Double today. None of the 13 lever-ceiling investigations covered this inter-stage representation cost (they targeted entropy/DWT loop bodies); the v10.0 Phase 8 wall budget bucketed the Int32->Double conversion inside the iDWT stage timing, hiding it.

**Evidence:** Line 4852-4858: '// Convert flat [Int32] → [Double] with vDSP ... vDSP_vflt32D(src.baseAddress!, 1, &out, 1, vDSP_Length(n))'. Line 5235-5241: 'The "remove or defer to final API boundary" rule from the v5.9 plan would require plumbing buffers through to the colour-transform / DC-offset / pixel-byte stages — bigger scope tracked for a follow-up; this lift is the SIMD shape of the same operation.' componentData.append(vDSPConvert.int32sToDoubles(currentLL)). DecodedTile.rgb is [[Double]] (line 1169); reconstructImage re-quantizes: vDSP_vdpsp -> vDSP_vclip -> vDSP_vfixru16 then 'for i in 0..<pixelCount { u16Ptr[i] = u16Ptr[i].byteSwapped }' (lines 5670-5677).

**Adversarial verification:** Verified accurate at every cited line: vDSP_vflt32D at 4852-4858 (CPU) and int32sToDoubles at 5241 (GPU, with the v5.9 'follow-up' comment), 6 vDSP_vsaddD Double DC-unshift sites, DecodedTile.rgb/[[Double]] composite, and reconstructImage's Double→Float→UInt16 chunked re-quantization plus scalar byte-swap loop — and the conversion is indeed timed inside the recordInverseWaveletTransform bucket, hiding it from stage profiles. Not implemented anywhere (grep clean) and never measured: V10_3_IDWT_GAP_PROBE.md line 67 explicitly lists 'Phase 3 (Int32→Double conversion skip)' as deferred, and v10.3-research executed Phases 0-2-4 but never Phase 3; it does not rhyme with any washed lever (all 13 were loop-body/routing probes, this is allocation/copy elimination, the explicitly-wanted category). Impact is grounded in the repo's own v10.3 Phase 0 profile (visible tail: DX 5.1 ms, MG 14.7 ms, with the conversion cost hidden on top), but since an Int32 tail halves traffic rather than eliminating stages, realistic capture is ~2-4 ms DX (borderline vs the 3 ms gate) and ~6-12 ms on MG multi-tile where the [[Double]] composite doubles the win — medium impact stands, with large effort and a wide parity-sensitive surface (6+ decode path variants).

### [low impact / small effort] Default GPU iDWT path does per-level LL readback + re-upload because the multi-level fused branch is gated on the GPU-HT-entropy flag that v10.3.0 turned OFF
**Where:** `Sources/J2KCodec/J2KDecoderPipeline.swift:5145` · **Category:** gpu

In applyInverseWaveletTransformGPU the GPU-resident multi-level chaining path (inverse2DInt32MultiLevelFused — one command buffer, LL stays on GPU across levels) is selected by 'else if (useGPUHT || Self._gpuHTEntropyEnabled), metalSession != nil'. _gpuHTEntropyEnabled is an ENTROPY routing flag that defaults false since v10.3.0 (line 452-478), and useGPUHT is only true via the deprecated decodeWithGPUHT API. So every default decode (DX single-tile via decodeGPU/decode(), MG per-tile in decodeMultiTileGPU) falls into the per-level loop at lines 5198-5225: each of the 5 levels commits its own command buffer via 'currentLL = try await metalDWT.inverse2DInt32(...)', reads the intermediate LL back into a Swift [Int32], then re-uploads it as the next level's input. For DX that is ~17 MB of avoidable intermediate LL round-trip traffic plus 4 extra command-buffer syncs; MG per-tile multiplies by 4 tiles. This is exactly the v10.7-style hazard the project memory warns about: a previously-correct gate becoming wrong as flags evolve — when the entropy flag flipped OFF, the iDWT dispatch shape silently degraded as a side effect. Caveat for the A/B: the v10.1.0 tiled and v10.3.0 fused H+V kernel upgrades live inside the per-level inverse2DInt32; the multi-level fused path may need those kernels ported before it wins, and the JP3D inverse2DInt32MultiLevelFusedBatched work (v10.11.0) already proved bit-exact multi-level GPU-resident chaining. Recommended fix: decouple the gate (metalSession != nil alone), port tiled kernels into the fused chain, and A/B on DX + MG.

**Evidence:** Line 5145: '} else if (useGPUHT || Self._gpuHTEntropyEnabled), metalSession != nil {' selects metalDWT.inverse2DInt32MultiLevelFused (line 5190). Else-branch lines 5198-5224: 'for level in (1...levels).reversed() { ... currentLL = try await metalDWT.inverse2DInt32(subbands: subbandData, backend: .auto) }' — per-level await with [Int32] readback feeding the next iteration's 'll: currentLL' upload. _readGPUHTEntropyEnv() returns false by default since v10.3.0 (lines 454-479).

**Adversarial verification:** Verified verbatim: line 5145 gates inverse2DInt32MultiLevelFused on (useGPUHT || _gpuHTEntropyEnabled) which defaults false since v10.3.0 (line 478); metalSession is non-nil on all default entry points (J2KCodec.swift sets processShared) and gpuBatch is nil when the flag is off (same gate at lines 3338/3382), so default DX/MG-tile decodes really do take the per-level loop at 5198-5224 with per-level [Int32] readback — plus a cost the finding missed, inverse2DGPUInt32 allocates fresh device.makeBuffer per level instead of using the buffer pool, and the gate text is unchanged since v6.2.0 D4 when the flag was ON (genuine stale-gate hazard, never decoupled-A/B'd; v10.8 probed different DX levers). However the impact is overstated: (1) the kernel-porting caveat is moot — encodeInverse2DInt32 (line 4362) is shared by both paths and already routes to the v10.1/v10.3 tiled+fused kernels; (2) with gpuThreshold=256 it is 4 command buffers not 5, and the ~17 MB round-trip is unified-memory memcpy (~8.5 MB each way, sub-ms), not PCIe; (3) the v10.7 10-trial bench already bracketed this path-pair on DX (flag ON = fully-fused iDWT + GPU entropy vs OFF = per-level + NEON): 56.48 vs 56.13 ms, classified noise; and project precedent (v10.2.0 fused kernel: 2x DRAM saving on 17 MP MG for borderline 3-6 ms; v10.5 colblock 22 ms microbench washed; v10.24.2 row-band CPU iDWT targeting the same GPU dispatch/readback overhead washed) consistently shows iDWT-traffic savings underdelivering end-to-end on M2. Real, cheap, clean experiment worth running, but expected DX win is ~1-2 ms — likely below the 3 ms acceptance gate.

### [medium impact / small effort] decodePartial/decodeResolution parse the codestream 2-4 times, and peekMetadata copies every tile payload it then throws away
**Where:** `Sources/J2KCodec/J2KCodec.swift:1226` · **Category:** perf-product-layer

parseCodestream materialises every tile's payload via parseSOTMarker -> reader.readBytes -> Data.subdata (a full copy of the compressed bytes, J2KDecoderPipeline.swift:2490 + J2KBitReader.swift:177). DecoderPipeline.peekMetadata (J2KDecoderPipeline.swift:2051) runs that same full parse and discards the tiles — so peeking metadata on a 20-30 MB MG file copies 20-30 MB for nothing. The v10.4-10.8 partial-decode entry points stack these: decodePartialResolution (J2KCodec.swift:1216-1236) does peekMetadata + pipeline.decode(data) (which parses again); decodePartial (J2KAdvancedDecoding.swift:492-524) adds its own peekMetadata first (3 parses); decodeResolution with upscale=true peeks a 4th time (J2KAdvancedDecoding.swift:634). On the thumbnail path that v10.5.0 advertises as 3-8x faster, 2-3 redundant full parses with full-payload copies are a meaningful fraction of the reduced wall (the code's own comment estimates 2-5 ms per extra parse). Fix is small: (a) add a header-only peek mode that reader.skip()s tile payloads instead of readBytes; (b) parse once in the entry point and pass (metadata, tiles) into the pipeline instead of re-parsing.

**Evidence:** J2KCodec.swift:1221-1226: '// The peek pays one extra codestream parse (~2-5 ms)... let metadata = try DecoderPipeline.peekMetadata(data)' followed by 'return try await pipeline.decode(data)' (parses again). J2KAdvancedDecoding.swift:493: 'let metadata = try DecoderPipeline.peekMetadata(data)' then line 516 routes to decodePartialResolution (which peeks again). J2KBitReader.swift:172-180: readBytes returns 'data.subdata(in: bytePosition..<(bytePosition + count))' — an allocating copy. parseSOTMarker (J2KDecoderPipeline.swift:2490): 'let tileData = try reader.readBytes(dataLength)'.

**Adversarial verification:** Verified against the live code: peekMetadata (J2KDecoderPipeline.swift:2051) runs a full parseCodestream and discards tiles; parseSOTMarker:2490 materialises every tile payload via readBytes, which is an allocating data.subdata copy (Sources/J2KCore/J2KBitReader.swift:177 — finding mis-cited the module, content exact). decodePartialResolution (J2KCodec.swift:1226+1235) peeks then re-parses in pipeline.decode (no pre-parsed overload exists); decodePartial (J2KAdvancedDecoding.swift:493→516) stacks to 3 parses, decodeResolution upscale=true (line 634) also 3, decodeQuality (line 808) 2. No header-only peek mode or fix exists anywhere (grepped headerOnly/skipPayload/peekOnly; git log shows v10.10-v10.15 commits introduced and consciously accepted the cost, never optimized it), and it rhymes with no washed lever — it's product-layer copy/parse elimination, an explicitly wanted category. Impact tempered slightly: it does not touch the mainline decode() benchmark walls (one parse), the realistic worst case is 3 parses not 4, and the win lands only on the partial/ROI/thumbnail APIs — but on the advertised ~10-20 ms thumbnail walls, 1-2 redundant full parses at the code's own ~2-5 ms estimate is a meaningful fraction, and the fix (skip payloads in peek; parse once and pass through) is small and trivially bit-exact.

### [low impact / medium effort] Each decoded code-block's coefficients are materialised 3 times: C-decoder [UInt32] buffer, .map to a second [Int32] array, then scatter-copy into the subband buffer
**Where:** `Sources/J2KCodec/J2KHTConformantDispatch.swift:104` · **Category:** memory

On the default HT-conformant CPU path (C+NEON decoder, default-on since v10.0.0), per block: (1) decodeViaNEONHotPath allocates a fresh [UInt32] coefs (w*h) for the C kernel output (J2KHTConformantBlockDecoder.swift:131); (2) decodeCleanupConformant(rawBytes:missingMSBs:) then runs 'decoded.map { sign/magnitude shift }' allocating a SECOND full [Int32] array with a scalar conversion pass (J2KHTConformantDispatch.swift:104-108); (3) applyEntropyDecoding stores these in per-subband DecodedBlock lists and row-copies them into the subband coefficient buffer (J2KDecoderPipeline.swift:3777-3805). For DX (~6.4M coefficients across ~1600 64x64 blocks) that is two avoidable full coefficient passes (~75 MB traffic), ~3200 transient 16 KB allocations contending on the allocator across the parallel LPT buckets, plus the subband scatter. Structural fixes that avoid touching the (wash-listed) decode loop bodies: fold the sign-magnitude->Int32 conversion into the C kernel's existing output write (it already knows shift = 30 - missingMSBs), and/or have the C decoder write directly into a pre-allocated subband buffer with a row stride — subband dimensions are computable from the CodeBlockInfo list before entropy decode starts, and block rects within a subband are disjoint so parallel tasks can write without synchronisation.

**Evidence:** J2KHTConformantDispatch.swift:103-108: 'let shift = 30 - missingMSBs; return decoded.map { uint in let sign = (uint & 0x8000_0000) != 0; let mag = Int32((uint & 0x7FFF_FFFF) >> shift); return sign ? -mag : mag }' — second full array per block. J2KDecoderPipeline.swift:3777-3786: scatter loop 'dstBuf.baseAddress!.advanced(by: dstStart).update(from: srcBuf.baseAddress!.advanced(by: srcStart), count: copyCount)' — third pass. decodeViaNEONHotPath: 'var coefs = [UInt32](repeating: 0, count: width * height)' per block.

**Adversarial verification:** All three citations verify exactly: the per-block [UInt32] alloc (J2KHTConformantBlockDecoder.swift:131), the .map second [Int32] alloc with scalar sign-magnitude conversion (J2KHTConformantDispatch.swift:103-108), and the row-scatter into subband buffers (J2KDecoderPipeline.swift:3777-3786); there is even a fourth uncounted copy, [UInt8](block.data) per block at line 3591. The C kernel j2knhd_decode_block_ht32 has no stride or Int32-output variant (j2knhd.h:180 documents a dense row-major uint32 buffer), so the proposed fold-in is not implemented anywhere; the v5.9 zero-copy lane only bypasses the scatter for the GPU lossy float path, and this chain IS the default DX hot path (parallel branch at line 3590, GPU-HT entropy off since v10.3.0). It does not match any washed lever — it is copy/alloc elimination, not loop-body SIMD; v10.0 Phase 7's fusion wash was encoder-side only and Phase 8's decode budget never isolated this chain. Impact stays low: the map/alloc costs are amortized across the parallel LPT buckets, only the ~51 MB serial scatter (~0.5-1 ms) is undivided, so projected DX wall saving is ~1-2 ms — likely below the 3 ms default-on gate, matching the v8.5/v10.1 projection-closure pattern.

### [low impact / medium effort] Compressed block bytes are copied 3x before reaching the entropy decoder (tile subdata -> per-block subdata -> per-block [UInt8] conversion)
**Where:** `Sources/J2KCodec/J2KDecoderPipeline.swift:3591` · **Category:** memory

The compressed payload is copied once when parseSOTMarker extracts the tile (readBytes -> Data.subdata, line 2490), a second time when extractTileData slices each block's bytes (line 2759, again subdata per block — thousands of small Data allocations), and a third time when applyEntropyDecoding converts each block's Data to a fresh [UInt8] array to call the decoder ('[UInt8](block.data)' at lines 3591 and 3702, and again at 3394/925 when building GPU inputs). The C entry point ultimately only needs a base pointer + length. For a DX-class image this is ~2 extra copies of the full ~5-8 MB compressed stream plus 2x per-block allocation churn under the parallel task group. Fix: have CodeBlockInfo carry (offset, length) into the retained tile Data (or ArraySlice views), and call the C decoder via withUnsafeBytes on the original buffer — eliminating both the per-block subdata and the per-block Array conversion. This is never-audited glue code between parse and entropy, not a decode loop body.

**Evidence:** Line 3590-3592: 'coeffs = try htDecoder.decodeCleanupConformant(rawBytes: [UInt8](block.data), missingMSBs: block.zeroBitPlanes)' — Data->Array copy per block. Line 2759: 'let blockData = try reader.readBytes(pb.dataLength)' where readBytes = 'data.subdata(in:...)' (J2KBitReader.swift:177). CodeBlockInfo.data is a standalone Data (line 2506).

**Adversarial verification:** Verified all cited sites: tile-level subdata copy (J2KDecoderPipeline.swift:2490 via J2KCore/J2KBitReader.swift:177 'data.subdata'), per-block subdata (line 2759 into standalone CodeBlockInfo.data), and per-block [UInt8](block.data) at 3591/3702 feeding decodeCleanupConformant, whose default C+NEON path immediately does block.withUnsafeBufferPointer into j2knhd_decode_block_ht32 — so the Array copy is provably avoidable, and no zero-copy/(offset,length) path exists anywhere (grep clean; latest commit 2ec85ad reworked entropy scheduling but kept the copies). Two corrections deflate the claim: GPU-input sites 925/3848 are off the default path (_gpuHTEntropyEnabled defaults false since v10.3.0, decodeWithGPUHT dropped from auto in v9.6), and the third copy only affects the conformant-HT branch (EBCOT/non-conformant pass Data directly). Sized honestly: ~10-16 MB avoidable memcpy (~0.1-0.2 ms) + ~2-3K blocks x2 alloc/free+ARC churn (~0.5-2 ms) on a ~35-45 ms DX wall — real, never probed in the 13 lever investigations (all loop-body/routing), bit-exact by construction, but likely lands below the 3 ms default-on gate, the same projection regime that closed v8.5 (1.32 ms) and v10.1 (~1 ms short). Parallel-task malloc contention is the one unmeasured variable that could beat the projection.

### [low impact / small effort] GPU decode paths use the allocating colour transform instead of the in-place variant (3 extra full-image Double buffers for RGB images)
**Where:** `Sources/J2KCodec/J2KDecoderPipeline.swift:5437` · **Category:** memory

decodeSingleTileGPU (line 680) and decodeTilePayloadGPU (line 1434) call applyInverseColorTransformGPU which — despite the name — just forwards to the CPU applyInverseColorTransform (line 5444). That variant calls transform.inverseRCTDouble / inverseICT which allocate three fresh full-size [Double] buffers, while the CPU pipeline path already uses applyInverseColorTransformInPlace (line 5494) which was specifically written to 'avoid 2 large buffer allocations' using the steal pattern. For 3-component images on the (default-routed, >=4 MP) GPU path this is 3 avoidable full-image Double allocations + copies per decode. Zero impact on the single-component medical corpus (early return at components.count < 3), so this would not show in the medical gate — but it is a one-line fix for RGB/visible-light decodes and removes a misleading 'GPU' name.

**Evidence:** Lines 5437-5445: 'private func applyInverseColorTransformGPU(_ components: [[Double]] ...) ... return try applyInverseColorTransform(components, metadata: metadata)' — no GPU involved, non-in-place. CPU path at line 1110 uses 'try applyInverseColorTransformInPlace(&spatialData, metadata: metadata)' whose doc comment (5489-5493) says it saves 2x/1x large buffer allocations.

**Adversarial verification:** Confirmed by direct read: J2KDecoderPipeline.swift:5437-5445 shows applyInverseColorTransformGPU just forwards to the allocating applyInverseColorTransform, whose inverseRCTDouble (J2KColorTransform.swift:279-287) allocates 5 fresh full-size [Double] buffers on the vDSP path vs 1 temp for the in-place variant — the finding undercounts. GPU call sites (lines 680, 1434) and CPU in-place usage (1110, 1255, 1807, 1885) verified; no env flag or alternate routing exists, and the only commit touching the symbol (d7ae542, PR #281) left a docstring claiming it routes through applyInverseColorTransformInPlace when it does not — so this is a stale-doc/regression, not an already-implemented fix. Impact is correctly scoped low by the analyst: both functions early-return for <3 components, so the single-component medical corpus and all perf gates pay zero; only RGB/visible-light decodes in the 500K-15M px GPU router band benefit. No rhyme with any washed lever — this is allocation elimination plus a misleading-name/stale-doc cleanup, an explicitly wanted category, with a trivial fix (call the in-place variant on a var binding, matching the CPU path).

### [low impact / small effort] 16-bit output is always byte-swapped to big-endian; little-endian consumers (DICOM Explicit VR LE) pay two wasted full-image swap passes
**Where:** `Sources/J2KCodec/J2KDecoderPipeline.swift:5675` · **Category:** api

reconstructImage always converts 16-bit samples to big-endian on LE hosts via a dedicated full-image pass ('if hostIsLittleEndian { for i in 0..<pixelCount { u16Ptr[i] = u16Ptr[i].byteSwapped } }', duplicated for signed at 5690-5692), and the inline comment at 5714-5717 acknowledges 'Callers expecting little-endian output (e.g. DICOM Explicit VR LE transfer syntax) must byte-swap at integration.' Since J2KComponent already carries an explicit sampleByteOrder tag (line 5755), the decoder could emit host-native (LE) order and tag it accordingly — or accept a requested byte order in decode options — eliminating the decoder's swap pass AND the consumer's swap-back pass on the DICOMKit product path (2 full passes over 13-33 MB of output per decode). Needs coordination with downstream consumers that assume BE (CLI PGM/PPM writers), hence an opt-in option rather than a default change.

**Evidence:** Lines 5675-5677: 'if hostIsLittleEndian { for i in 0..<pixelCount { u16Ptr[i] = u16Ptr[i].byteSwapped } }'. Lines 5714-5717: '16-bit output: big-endian byte order (PGM / DICOM Explicit VR BE convention). Callers expecting little-endian output (e.g. DICOM Explicit VR LE transfer syntax) must byte-swap at integration.' Line 5755: 'sampleByteOrder: compInfo.bitDepth > 8 ? .bigEndian : nil' — the tagging mechanism for a configurable order already exists.

**Adversarial verification:** Confirmed: J2KDecoderPipeline.swift:5675-5677/5690-5692 unconditionally byte-swap 16-bit output to BE on LE hosts, and DICOMKit's packPixels (J2KSwiftCodec.swift:549,570) swaps it straight back via vImageByteSwap_Planar16U — plus a hidden CoW full-buffer copy from the in-place mutation, so the product path pays swap+copy+swap. Not previously tried: no decode-side byte-order option or env flag exists; the encode direction got exactly this fix (DICOMKit's .littleEndian hint, 'saves us the O(N) manual swap'), and JP3D already emits .littleEndian-tagged output, so the pattern is precedented and doesn't rhyme with any washed lever. Impact is modest though: the passes are bandwidth-bound (~1-2.5 ms combined on 33 MB MG-class, <1.5 ms DX), below the 3 ms gate for the in-codec half, and the larger saving lands in DICOMKit outside the quoted benchmark; opt-in scoping is correct since CLI PGM writers and the daemon decodeFile raw path assume BE.

## Dimension: encoder-pipeline (3 confirmed)

> **Analyst summary:** The encoder pipeline's lossless fast paths are largely in place (rate control, layer truncation, and adaptive-step building all short-circuit for lossless), and the HT entropy loop bodies are confirmed at their lever ceiling — so the remaining encoder opportunities are structural, not loop-level. The production path for all medical fixtures ≥500K px is encodeNativeMultiTile (planner .auto since v7.0.0), and several decisions tuned in the single-tile era have never been re-audited on that baseline. The strongest finding is a v10.7-pattern stale default: the GPU forward 5/3 DWT pixel threshold (3 MP) was designed to exclude multi-tile per-tile dispatches, but the v9.6 MG 2x2 override produces 4.21 MP tiles that breach it — four concurrent per-tile GPU DWT dispatches now serialize through one MTLCommandQueue on MG, the exact configuration the in-code measurement table records as a 34-44% DWT loss. Second tier: avoidable staging copies and allocations clustered around the forward-DWT-dominated wall — two full-image memcpys per level in the parallel column pass, a fresh DWT scratch pool allocated per level because the v6-alpha4 Lever A pooled recursion has no production caller, a per-code-block 16 KB Array copy in the fused entropy loop, full-image zero-fill + a separate DC-shift pass in preprocessing, a per-tile pixel-slab copy in sliceTile, and a triple copy of the compressed payload during codestream assembly. Each is individually ~0.5-2 ms on DX/MG-class fixtures (below the 3 ms gate alone) but they are additive and all bit-exact-safe. Also flagged: always-on per-block NSLock+clock instrumentation in writePacket, and nested per-tile entropy/DWT task spawning inside already-saturated multi-tile task groups. Overflow not reported as findings: per-pixel signed branch in the 8-bit extract loop, sorted()+map materialization of fused-entropy results, and the bounded j2kInfer16BitByteOrder re-run per tile when sampleByteOrder is nil.

### [low impact / small effort] Stale GPU routing: per-tile GPU forward DWT fires on MG 2x2 production tiles, violating the threshold's documented design intent
**Where:** `Sources/J2KCodec/J2KEncoderPipeline.swift:2865` · **Category:** gpu

The GPU forward 5/3 gate is `_gpuForward53Enabled && metalAvailable && pixels >= 3_000_000` with NO multi-tile predicate. The in-code rationale (lines 2840-2857) says the threshold deliberately 'excludes multi-tile per-tile dispatches (per-tile dim is always ≪ 4 MP for the production .auto layouts)' because concurrent per-tile dispatches 'serialise through one MTLCommandQueue', measured at GPU −34% to −44% vs CPU. That invariant was broken twice since: E2 lowered the threshold 4 MP→3 MP (v6.3.0, single-tile era), and the v9.6 planner override gives MG-class images 2x2 tiles of 1759×2392 = 4.21 MP ≥ 3 MP (J2KEncodeTilePlanner.swift:211). So on the production .auto path, the ONLY consumer of GPU forward DWT is exactly the multi-tile-concurrent configuration the table says loses. ## Dimension: memory-allocations (6 confirmed)

> **Analyst summary:** Allocation/copy hygiene in J2KCodec/J2KCore is strongly bimodal: every code path that a past research arc touched (encode HT entropy with hoisted raw-pointer buffers, forward-DWT band arrays via unsafeUninitializedCapacity, the flat multi-level iDWT, vDSP dequant/reconstruct) is already exemplary, but the seams BETWEEN those optimized stages still carry systematic per-block and per-frame copies that no investigation has audited. The two strongest decode findings sit on the production conformant-HT path: each code-block's coefficients are materialized twice (a fresh [Int32] from a `.map` sign-magnitude conversion that could be fused into the existing subband scatter) and each block's compressed bytes are heap-copied twice (Data.subdata in readBytes, then [UInt8](block.data)) — a pattern the EBCOT path already fixed but the HT path never received. On encode, the parallel-column forward 5/3 DWT performs two avoidable full-frame memcpys per decomposition level (~80 MB per DX component) purely for pointer-stability bookkeeping, on the stage measured at ~60% of encode wall. Larger-effort structural items: the reversible decode tail converts exact Int32 iDWT output to full-image [Double] for DC-shift/composite/reconstruct (8 B/px where 4 would do), and multi-tile decode zero-fills 135 MB Double canvases that compositing fully overwrites. Finally, ~970 lines of buffer-pool/allocator infrastructure (J2KBufferPool, J2KHTBlockCoderPooled, J2KMemoryPool, J2KOptimizedAllocator, J2KZeroCopyBuffer) are dead weight with zero production callers — the answer to 'does pool infrastructure exist but go unused' is yes, entirely. Individual items are mostly in the 0.5-2 ms band on DX/MG; the per-block coefficient fusion plus the encode DWT copy elimination are the two most plausible candidates to clear the 3 ms gate, and several findings compound on the same fixtures. Minor overflow not reported in detail: scalar byte-swap loops in reconstructImage (likely auto-vectorized), Part-2 MCT Int32->Double nested maps (off the medical path), and jagged-array DWT variants confirmed reachable only from non-production odd-origin/lossy-conservative branches.

### [low impact / small effort] Production HT decode allocates a second full coefficient array per code-block via .map (sign-mag conversion not fused into scatter)
**Where:** `Sources/J2KCodec/J2KHTConformantDispatch.swift:104` · **Category:** perf-hot-path

On the default decode path (conformant HT, C+NEON decoder), every code-block's coefficients are materialized twice before reaching the subband buffer: (1) decodeViaNEONHotPath fills a zero-initialized [UInt32] (J2KHTConformantBlockDecoder.swift:131); (2) decodeCleanupConformant(rawBytes:) then runs `decoded.map { ... sign/mag shift ... }` allocating a fresh [Int32] of the same size; (3) applyEntropyDecoding scatters that array into subbandCoeffs (J2KDecoderPipeline.swift:3777-3787). The .map pass is fully avoidable: fold the UInt32 sign-magnitude -> Int32 conversion into the existing scatter loop (read the UInt32 buffer, convert per element while writing into subbandCoeffs), eliminating one full-size heap allocation plus one write+read pass per block. On DX-class (7.8M coeffs, ~1900 blocks) that is ~31 MB of avoidable alloc+write+read plus ~1900 allocations; ~2x that on MG 17 MP. Notably the ENCODE side received exactly this treatment in v9.x ('Phase 3a skips the 4 per-block Array extraction allocs', J2KEncoderPipeline.swift:5591-5594) but the decode dispatch layer was never given the same audit (file untouched since v9.3.0 per git log). This is allocation/copy elimination, not a loop-body micro-opt, and entropy is 57% of the DX decode wall.

**Evidence:** J2KHTConformantDispatch.swift:98-108: `let decoded = try HTBlockDecoderConformant.decode(block: rawBytes, ...)\n let shift = 30 - missingMSBs\n return decoded.map { uint in let sign = (uint & 0x8000_0000) != 0; let mag = Int32((uint & 0x7FFF_FFFF) >> shift); return sign ? -mag : mag }` — fresh width*height [Int32] per block, immediately followed by another full copy in the scatter at J2KDecoderPipeline.swift:3785-3786 (`dstBuf.baseAddress!.advanced(by: dstStart).update(from: srcBuf...)`).

**Adversarial verification:** Factually accurate and on the default hot path: the .map at J2KHTConformantDispatch.swift:104 allocates a fresh [Int32] per block, the C+NEON decoder already filled a [UInt32] (J2KHTConformantBlockDecoder.swift:131), the scatter (J2KDecoderPipeline.swift:3777-3787) is a third pass, and _gpuHTEntropyEnabled=false since v10.3.0 means no GPU bypass; no Int32-output C variant or flag exists. But impact is overstated on three grounds: (1) the sign-mag conversion itself is unavoidable — only the alloc plus one L2-resident 16KB-per-block copy pass is saved; (2) the proposed fusion target is wrong — the .map runs inside the PARALLEL task group (line 3590) while the scatter loop is SEQUENTIAL, so folding conversion into the scatter would serialize ~7.8M conversions and plausibly regress; the safe variant (in-place convert in the parallel task) saves ~2-4 ms CPU ÷ ~5x parallelism ≈ 0.5-1 ms wall on DX, below the 3 ms gate; (3) direct historical precedent: commit 5b58eb2 (v9.1 Phase 2d) eliminated 2,500-7,500 per-block buffer allocations on the encode block path and settled at -0.46 ms ("19th lever-ceiling wash"), with the commit message explicitly noting per-block alloc cost is masked by other per-block work including sign-magnitude conversion — the finding's "encode got this treatment" argument actually predicts a wash, not a win. Real allocation waste, cheap to fix as hygiene, but very unlikely to clear the 3 ms default-on acceptance bar.

## Dimension: metal-gpu (10 confirmed)

> **Analyst summary:** The J2KMetal layer is mature in places (heap-backed buffer pool, cached PSOs, single-command-buffer fused multi-level IDWT, async cb.completed() instead of waitUntilCompleted, VLC tables cached, fresh-queue fix on the encode side) but the audit found a consistent pattern: optimizations landed on one path and never propagated to its siblings, and v10.3.0's entropy-flag flip silently degraded the GPU IDWT dispatch shape. The most significant findings: (1) the bit-exact fused multi-level 5/3 GPU IDWT — single command buffer, pooled buffers, GPU-resident level chaining — has been unreachable on every default decode route since v10.3.0 because its gate couples it to the now-off GPU-HT-entropy flag, so production runs a per-level loop with per-level commit/readback/re-upload; (2) that live per-level path (inverse2DGPUInt32) bypasses the buffer pool entirely with 7 raw makeBuffer calls per level; (3) the documented release-mode readback deadlock pattern (withUnsafeMutableBytes+copyBytes from MTLBuffer.contents() right after await cb.completed()) survives in readFloatArray — on the live 9/7 lossy session decode path — and in the GPU colour-transform readbacks, despite being fixed in readInt32Array and the HT paths; (4) preWarm()'s pipeline list predates v10.x and warms neither the tiled nor the fused 5/3 kernels that lossless production decode uses, and its warmup dispatch is lossy 9/7, leaving the product's primary path cold; (5) concurrent multi-tile decode IDWT serializes on the single shared MTLCommandQueue while the encode side already adopted fresh queues after measuring a 33-43% regression from exactly this. Secondary findings cover pool config (power-of-two bucketing + 256MB caps that drop/re-allocate the large-fixture buffers v10.3.0 newly routes to GPU), dead colLow/colHigh acquisitions on the fused path, JP3D batched paths bypassing the pool, arbitrary PSO-cache eviction at a 32-entry cap, and the avoidable MTLBuffer→[Int32]→[Double] double-pass readback for which an unused-on-decode zero-copy view type already exists. None of these touch HT entropy loop bodies or DWT inner lifting; all are scheduling/allocation/coverage gaps orthogonal to the 13 confirmed lever-ceiling investigations. Findings 1+2+10 interact and are best measured as one A/B (re-gate fused path on metalSession, pool the buffers, view-based readback); finding 3 is correctness-adjacent and should be fixed regardless of perf.

### [low impact / small effort] Fused multi-level 5/3 GPU IDWT is dead-gated on default decode routes since v10.3.0 — per-level command buffers with inter-level readback/re-upload run instead
**Where:** `Sources/J2KCodec/J2KDecoderPipeline.swift:5145` · **Category:** perf-hot-path

The reversible-5/3 multi-level fused GPU IDWT (inverse2DInt32MultiLevelFused: ONE command buffer for all levels, pooled buffers, LL chained GPU-resident between levels, single final readback) is gated on `(useGPUHT || Self._gpuHTEntropyEnabled), metalSession != nil`. `useGPUHT` is only set by the explicit decodeWithGPUHT API, and `_gpuHTEntropyEnabled` was flipped to default-false in v10.3.0 (commit 4126ffb). Consequently the default decode()/decodeGPU() routes (which DO fire for >=4MP single-tile per `_gpuInverse53Enabled=true` + 4MP threshold, i.e. DX/PX class, and for multi-tile >=1MP tiles, i.e. MG 2x2) fall into the per-level else-branch (lines 5198-5225) calling `metalDWT.inverse2DInt32(subbands:, backend: .auto)` once per decomposition level — each level pays its own command buffer commit + await, a full readback of the level output, and a CPU-side re-upload of that output as the next level's LL. ## Completeness critique of the 8-dimension audit

### 1. Subsystems no dimension examined (~26K lines, ~15% of Sources/, zero coverage)

Sources/ contains 23 directories; cross-checking against the eight summaries:

- **JPIP — 13,955 lines, entirely unaudited.** Sources/JPIP/ is live product surface (wired into the CLI via Sources/J2KCLI/JPIPClient.swift and JPIPServer.swift) with 30 files including WebSocket servers, bandwidth estimators, precinct caches, and a JP3D streaming stack. build-health explicitly said JPIP "was not flagged" because it is live — but being live is precisely why it needed an audit, and no dimension owned it. It contains shipped TODO stubs (JPIP.swift:109/144 — responses parsed into nothing) and the same Data-copy patterns flagged elsewhere. This is the largest single gap.
- **J2KFileFormat — 12,052 lines, entirely unaudited.** Includes the JP2/JPX box layer plus a complete Motion JPEG 2000 (MJ2) sub-stack (9 files: MJ2Creator/Player/Extractor/StreamWriter/SampleTable...) that has **zero callers in J2KCLI or J2KCodec** — likely test-only dead weight on the scale of the flagged J2KVulkan. The module also has 288 per-byte `data[...]` subscript accesses, the exact cost class new-arcs flagged in JP3D.
- **J2KAccelerate — the dead-code finding is understated by ~5x.** build-health flagged only the ~2.1K-line x86 subdirectories. In fact there are **zero `import J2KAccelerate` statements across J2KCodec, J2K3D, J2KCLI, and J2KMetal** — the entire 10,120-line target (J2KAcceleratedTrellis/Perceptual/NLT/ROI/MCT/Wavelet, DeepIntegration, VImageIntegration, JP3DAcceleratedDWT) is production-dead, not just its x86 corner.
- **J2KCodecNEON (2,510 lines C)** — the Swift↔C boundary was audited from the Swift side (decode triple-materialization finding), and I verified the encode-side boundary is already clean (hoisted caller-owned buffers in J2KHTConformantBlockEncoder.swift), but the C files' internal allocation/staging behavior had no reviewer. Defensible given the hot-path ban; noting for completeness.
- Minor: AppFlowTest (364 lines) and J2KBenchApp (a bare .xcodeproj) were not named by build-health's "five orphaned directories" list explicitly (only DiagTest was named); CZlib is a 1-line shim (fine); J2KTestApp as its own target is correctly separated and was reasonably skipped.

### 2. Optimization categories not considered

- **Test/CI wall time** — 18 test targets plus PerformanceTests; commit gate runs 7 suites per commit; nobody examined suite runtime, fixture corpus duplication, or the stale-bundle hazard MEMORY already documents as a recurring footgun.
- **Energy/thermal efficiency** — the product targets A-series (battery) devices; concurrency covered QoS only as a perf lever, never sustained-power or E-core *intentional* use for background daemon work.
- **Binary size as a measured quantity** — dead-weight findings imply it, but no dimension measured the 14.6 MB CLI breakdown, metallib size, or `-dead_strip`/strip settings; with ~35-40K dead lines identified, the size win is quantifiable and unclaimed.
- **Public API shape as a perf root cause** — J2KComponent stores samples as raw big-endian `Data` with a ByteOrder enum (J2KCore.swift:227+). No dimension flagged that the API itself forces byte-packing round-trips on every producer/consumer.

### 3. Findings sanity-checked

Confirmed accurate: unsafeFlags at Package.swift:109/135; dead `J2K_GPU_HT_ENTROPY` setenv at Commands.swift:480 vs the pipeline reading `J2K_GPU_HT_ENTROPY_DECODE` (J2KDecoderPipeline.swift:455); the high-rated CLI finding — `--level` parsed at Commands.swift:448, echoed at 486, documented at 664, and `decodeResolution` never called. One impact dispute: the decoder-pipeline finding #2 and metal-gpu finding #1 are the **same root cause filed twice** (fused multi-level IDWT gated on the entropy flag v10.3.0 disabled), each rated "low" — deduplicated and considered as the single default-path regression it is, it is plausibly medium. Conversely, the wrapInJP2Container finding is *cheaper* than stated: J2KCLI/main.swift already imports J2KFileFormat, which contains a real box writer with jp2h/superbox support — the fix is wiring, not new code.

### 4. Cross-cutting opportunities the per-dimension view missed

- **One API change collapses four findings.** The 16-bit big-endian swap passes (decoder), DICOM double-copy + LE consumers (new-arcs), JP3D per-byte voxel subscripts (new-arcs), and PPM/PGM byte loops (daemon-cli) all stem from J2KComponent's bytes-as-Data contract. A typed UInt16/Int32 buffer accessor (or native-endian output option) is the shared fix; no dimension proposed it because each saw only its local symptom.
- **The "stale gate" pattern recurred in four dimensions** (fused-IDWT entropy-flag coupling, MG 2x2 GPU-DWT threshold breach, CLI's J2K_GPU_INVERSE_53=0, stale preWarm kernel list) — exactly the v10.7 lesson. The meta-fix nobody proposed: a one-time inventory of every env-var/threshold gate annotated with the version whose measurements justified it, re-validated per release. That would systematically catch the next instance instead of waiting for a research arc to trip over it.
- **Dead-code elimination should be one arc, not seven findings.** Pool infra (~970), concurrency infra (~900), J2KCore scaffolding (~13.6K), J2KVulkan (3K), J2KXS (1.5K), .custom HT (4.5K), x86 (2.1K), plus my additions (J2KAccelerate ~10K, MJ2 ~several K) total ~38K lines. Doing it as one pass also strengthens the build-health cross-module-optimization A/B, whose benefit is diluted while dead code inflates module surfaces.
- **preWarm fixes compound across dimensions:** metal-gpu's stale-pipeline-list finding is worth little unless daemon-cli's never-prewarm-at-launchd finding is fixed in the same change; they should be one A/B, not two.
- **Buffer lifetime is one arc:** GPU pool bucketing/cap defeat (metal), per-level raw makeBuffer (metal), JP3D pool bypass (metal), and the dead CPU-side pool modules (memory) are a single ownership-design problem.

### Overall confidence

Coverage of the audited dimensions is strong — J2KCodec, J2KMetal, concurrency, daemon/CLI, and build configuration were examined at high resolution, and spot-checks confirm the findings I tested. But the audit was scoped by *recent activity* rather than by directory inventory: roughly 26K lines of live, CLI-reachable product surface (JPIP, J2KFileFormat including MJ2) received zero examination, one dead-weight finding undercounts by ~8K lines (all of J2KAccelerate, not just x86), and the strongest cross-cutting levers (typed-sample API, stale-gate inventory, consolidated dead-code arc) are visible only across dimension boundaries. I'd call the audit ~80-85% complete by line coverage of in-scope production code, with the JPIP and J2KFileFormat gaps being the only ones large enough to plausibly hide medium-impact findings.
