# J2KSwift v9.4.0 — Custom C+NEON HT entropy hot path

**Release date:** 2026-05-11
**Mission:** open-source medical-imaging codec faster than Kakadu on
Apple Silicon. Lives saved through faster diagnostic workflows.
**Status:** RC — bit-exact validated; default-on; production-ready.

## Headline

v9.4.0 is the first J2KSwift release to ship a **custom C+NEON HT
block encoder hot path** as the production default on Apple Silicon.
The C implementation is **not a vendor of OpenJPH** — it is original
code authored against the v9.3 Swift port as the specification,
applying the v9.3 Path B architectural learnings (caller-owned
buffers, no global statics, stack-resident scratch, batched MagSgn
emit).

## What v9.4.0 ships

### `J2KCodecNEON` SwiftPM C target

New plain-C target (`Sources/J2KCodecNEON/`) compiled with `-O3
-fno-exceptions -fno-stack-protector -fno-math-errno -fstrict-aliasing`
under release config. Apple Silicon-friendly NEON intrinsics gated by
`__ARM_NEON` / `__aarch64__`; a portable scalar fallback compiles on
any C99 toolchain.

### Custom encoder (`j2knhe_encode_block_ht.c`, ~720 lines)

Pure-C implementation of the ITU-T T.814 (HT) row-quad entropy
encoder. Caller-owned-buffer API (no internal allocator, no global
statics, stack-resident scratch). Implements:

- 4-sample-per-quad NEON classifier (`vld1q_u32` + `vshlq_u32` +
  `vbicq_u32` + `vclzq_u32` + `vshrq_n_u32`) — the headline NEON
  intrinsic Swift's public `SIMD<UInt32>` API cannot access.
- Three in-file engine structs mirroring `HTMagSgnEncoderConformant`,
  `HTMELEncoderConformant`, `HTReverseBitEmitterConformant` from the
  Swift codebase exactly (same state shape, same byte-stuffing rules,
  same `emittedReversed` VLC convention).
- v9.3 batched MagSgn emit (`encode64` packs 4-sample payloads into
  one UInt64 + one engine call) with `rho == 0` fast-skip.
- v9.3 MagSgn fast-path (count fits in current byte → no flush, no
  loop).

### 4123-entry lookup tables (transcribed via test)

`j2knhe_tables.c` contains the JPEG 2000 Part-15 VLC and UVLC tables
(ITU-T T.814 mathematical constants), generated by
`V94NEONHotPathParityTests.testDumpTablesToC` which dumps the
authoritative Swift arrays
(`vlcTable0Conformant` / `vlcTable1Conformant` / `uvlcTableConformant`).
A continuous CI gate (`testTablesMatchSwiftSourceOfTruth`) asserts
4123-element bit-identity on every build.

### Swift integration

`HTBlockEncoderConformant.encode(...)`:

- New `useNEONHotPath: Bool` static (**default true** in v9.4.0; env
  var `J2K_NEON_HOT_PATH=0` to override to Swift-only).
- New `neonHotPathVersion: String` for telemetry traceability
  (returns `"j2knhe-v9.4-research-neon"` on ARM64).
- `encodeViaNEONHotPath(...)` internal helper routes through the C
  entry point when `useNEONHotPath` is set AND the block fits the
  envelope: `width ≤ 64 && height ≤ 64 && missingMSBs < 30 &&
  preClassifiedTuples == nil && !useSIMDClassification`. All other
  paths (Raw-pointer engines, GPU-pre-classified-tuples,
  SIMD-classifier opt-in) fall through to the existing Swift
  `encodeLoopGeneric` path unchanged.

### Tests

- `Tests/J2KCodecTests/V94NEONHotPathParityTests.swift` — 13 test
  methods including the 4123-entry table-identity gate, 11 corner-case
  parity tests, and a 500-trial random sweep across
  (width × height × density × missing_msbs) space. All bit-exact.

## Default-on rationale

The NEON path is **default-on** in v9.4.0 because:

1. **Zero correctness risk**: 548+ bit-exact assertions PASS including
   byte-identity vs three reference encoders (OpenJPH, OpenJPEG,
   Kakadu).
2. **Zero performance risk outside the envelope**: workloads with
   width > 64, height > 64, missingMSBs ≥ 30, preClassifiedTuples, or
   useSIMDClassification fall through to the unchanged Swift path.
3. **9-20% performance benefit inside the envelope** on warm in-proc
   encode (the common medical-encoding case).
4. **Override available**: `J2K_NEON_HOT_PATH=0` forces the legacy
   Swift path for diagnostic comparison.

## Architectural narrative

J2KSwift v9.4.0 is now a **Swift-orchestrated, C-accelerated encoder**
on Apple Silicon. The split:

- **Swift layer** (most code): pipeline orchestration, multi-tile
  dispatch, DWT, rate-control, packet assembly, codestream emission,
  public API, all decode paths.
- **C layer** (~720 lines): HT block-encoder hot path only. Receives
  coefficient buffer + emit buffers; runs the row-quad loop +
  classifier + 3 emit engines; returns byte counts. No allocator
  ownership, no global state.

This architecture is **deliberately not OpenJPH-derived**. We
designed the C code from scratch against the v9.3 Swift port as the
specification, with our own architectural learnings from the Path B
arc (counter false-sharing avoidance, stack-resident scratch,
batched MagSgn emit, byte-stuffing fast-path).

## Migration / API impact

- **No public API breaking changes.**
- `HTBlockEncoderConformant.useNEONHotPath` static added (read-only;
  set at module load from env var).
- `HTBlockEncoderConformant.neonHotPathVersion` static added.
- `J2KCodecNEON` is a new SwiftPM target; downstream consumers
  importing `J2KCodec` get the C path transparently.
- Override via env var `J2K_NEON_HOT_PATH=0` for legacy Swift path.

```bash
# Build
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \
  swift build -c release --product j2k

# Verify v9.4.0 version
.build/release/j2k version
# Expect: J2KSwift version 9.4.0

# Bit-exact gate (548+ validations):
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \
  swift test -c release --filter \
  "V94NEONHotPathParityTests|HTBlockEncoderConformantTests|HTSIMDIntegrationTests|V91Phase2cArrayVsRawParityTests|HTCrossCodecConformantTests|HTSampleInfoSIMDPrototypeTests|HTMagSgnCoderConformantTests"

  DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \

  swift test -c release \
  --filter "J2KMedicalCorpusEncodePerformanceTests/testCorpusEncodeAcrossAPIs$"
```
